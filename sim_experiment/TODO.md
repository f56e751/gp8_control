## 배경 (2026-11-18 확인)

- RL 정책은 "어느 물체를 throw/push 할지" 고르는 상위 결정만 한다. 궤적은 실기와 같은 스킬 코드(`skills/throw_skill.py`, `skills/push_skill.py`)가 만든다. 문서: `docs/rl_simulator_status_2026-10-10.md`.
- 보상은 스킬과 무관하게 "물체가 자기 클래스 통에 들어갔나"다. 자기 통 +1, 잡거나 밀었는데 다른 곳 −0.3, 건드리지 않았는데 옆에서 떨어뜨림 −0.3, 실행 실패 −0.3 추가.
- 기존 기록: "PPO가 throw만 쓰는 정책으로 수렴하기 쉽다, push는 metal을 아예 못 집게 해야 자주 나온다."
- **벽(가드) = 벨트에서 통 반대편, 로봇 쪽 가장자리의 가드.** push는 물체 뒤(로봇 쪽)로 0.20 m 물러났다가(백스윙) 통 쪽으로 미는데, 이 가드 때문에 백스윙을 충분히 못 한다.
  - sim에는 가드 형상이 없다. 가드는 `skills/push_skill.py`의 숫자 두 개로만 표현된다.
    - `PUSH_EXEC_MIN_BACKSWING_X = 0.24`: 백스윙 시작점이 x < 0.24 m면 그 물체는 push 후보에서 빠진다. RL 시뮬레이터에서는 행동 마스크에서 빠져 정책이 고를 수조차 없다.
    - `PUSH_RETREAT_MIN_X = 0.25`: 실행할 때 백스윙이 x 0.25 m보다 안쪽으로 못 가게 도움닫기를 줄인다.
  - 손대지 않는 것: 팔 도달 거리(`cfg.MAX_REACH` 0.65 m) 제한, 백스윙 자세의 역기구학(IK)이 실패할 때 쓰는 대체 동작.

1. **RL이 push를 안 고른 원인 = sim과 실기의 인식 지연 차이.** push 코드의 실기용 보정(0.28 s 일찍 치기)이 지연 없는 sim에서 push를 헛치게 만들었다(성공률 약 50%). 그래서 RL이 push를 피했다.
   - 같은 설정에서 보정값만 바꾸면 push 선택이 2~4% ↔ 45~50%로 바뀐다(E1 vs E1b).
2. **가드(벽) 제한을 없애면 push가 더 많이 쓰인다**(push 선택 54% → 80%, 평균 보상 57.0 → 63.7). 다만 보상 차이는 seed 편차가 커서 약한 근거다. 가드는 원인이 아니라 추가 이득 요인이다.
3. **sim 물리 이상(관통·튕김)은 실패 원인이 아니다.** 큰 관통은 고속 충돌에서 생기고, 오히려 성공한 push에서 많다.
4. **남은 push 실패는 기하 문제다.** metal을 흐름 거슬러 45° 넘게 비스듬히 밀면 두 통 사이로 떨어진다(성공 50% 이하). 스킬 계획 개선 후보.
5. **sim 표준 설정 제안**: `GP8_SIM_PERCEPTION_LAG=0.28` + 실기 보정 그대로. throw는 지연에 둔감하고, push는 지연·보정 차이 ±0.08 s 안이면 정상이다.
6. 10만 step 학습 정책은 규칙 정책보다 아직 못하다 → 학습 연장(E6).
7. (E6, 23:50 추가) 실기와 같은 설정(sim 지연 0.28 + 실기 보정)에서 30만 step 학습하면 push를 적극적으로 고른다. 가드 끔이면 규칙 정책과 같거나 낫고(65~71 vs 65), 가드 켬이면 낮다(50~55 vs 62). 가드 켬의 손해는 처리 순서 문제(하류 물체를 두고 상류 물체를 골라 놓침)다. seed 2·3 추가 확인 중(E7).
   - 평가 step 상한 1000이 skip 많은 정책을 잘라 보상을 낮게 보이게 했다 → 8000으로 수정.
8. (E7, 11-19 04:00 추가) 학습 seed 4개 기준: 가드 끔 평균 68.9(4개 모두 규칙 65.3 이상), 가드 켬 평균 59.0(1개만 규칙 62.1을 넘음). 차이는 처리 순서를 배웠는지(놓친 물체 수)로 거의 다 설명된다.

### E0 / E0b 결과 요약 (2026-11-18)

1. **가드(벽) 제한의 영향은 작다.** 가드를 끄면 push 허용 비율이 0.52 → 0.58 (현행 규칙), 0.36 → 0.40 (push 우선). push를 막는 더 큰 요인은 팔 도달 거리(백스윙이 반경 0.65 m 밖) 제한과 intercept 불가다.
2. **sim의 push가 절반 가까이 헛친 원인 = 실기용 인식 지연 보정 `PUSH_PERCEPTION_LAG = 0.28 s`.** 실기는 인식이 0.28 s 늦어 일찍 쏘도록 맞춘 값인데, 학습 sim은 지연 없는 실제 위치를 쓴다. 그래서 패들이 0.28 s × 벨트 속도(3~8 cm)만큼 물체 앞을 친다.
   - 증거: 0.28 s에서는 벨트가 빠를수록 성공률이 급락한다(0.10 m/s 84% → 0.30 m/s 25%). 0 s로 하면 71~88%로 속도와 무관하다.
   - push 우선 정책의 자기 통 성공률: metal 48% → **77%**, transparent 53% → **91%**. 에피소드 보상 28.0 → **60.9** (throw 우선은 45.7, metal throw 성공률 49%).
   - 이전 "헛친 push"는 벨트 위에 그대로 남아 하류로 흘러갔다(최대 속도 0.5~1.5 m/s, 패들은 2 m/s).
   - → 지금까지 RL이 push를 안 고른 주된 이유일 가능성이 크다. E1·E1b로 확인한다.
3. **물리 이상 플래그는 실패 원인이 아니다.**
   - 관통(>5 mm)은 주로 빠르게 날아간 물체가 통 벽이나 다른 물체와 부딪힐 때 생긴다. 그래서 성공한 push에서 더 많다(관통 있음 61% 성공, 없음 41%).
   - 패들보다 빠른 속도(p95 ≈ 3.1 m/s)는 가벼운 물체 탄성 충돌의 범위(최대 2배) 안이다.
   - 위로 튐 ~1%. 벨트를 파고드는 경우는 거의 없다.
   - 실제와 같은지는 2번(실기 비교)에서 확인해야 한다.
4. **보정 후 남은 실패(metal 23%)**: 대부분 두 통 사이 바닥(y≈0.3)에 떨어진다.
   - metal 통(y=0.6)이 push 지점보다 벨트 상류에 있어 흐름을 거슬러 비스듬히 밀어야 한다. 물체가 벨트 위를 미끄러지는 동안 하류로 끌려간다(영상 확인).
   - 후보 대책: 조준 보정, 또는 상류에서 치기. 벨트 마찰이 실제와 같은지도 2번에서 확인.
5. 현행 규칙(metal→push, transparent→throw)은 보정 0.28 s 상태에서 에피소드 보상 51.7. 보정 0으로 다시 잰 값은 E0 재실행 결과에서.

### sim에 인식 지연이 없는 이유 (2026-11-18 조사)

- 학습에 실제 위치(truth tracks)를 쓰는 것은 의도된 단순화다. 10-01 문서에 "첫 RL 작업에서 인식·위치 추정 오차를 빼기 위해"라고 적혀 있다. 카메라식 관측은 보상이 더 낮고 불안정했다.
- sim 검출의 지연 0(`backends/mujoco_sim.py` "zero latency in sim", `perception_delay_s: 0.0`)은 근거가 적혀 있지 않다(커밋 66482d8, 2026-08-29).
  - 추정: 실기는 `camera_debug`가 촬영→수신 지연을 보정하므로 "보정 후 = 지연 0"으로 본 것 같다.
  - push의 0.28 s는 그 보정 뒤에도 남는 지연을 실기 타격 실험으로 잰 값이라 sim에 빠져 있다.
  - throw는 스킬 쪽 보정(`TRACK_LEAD_T`)이 기본 0이라 영향이 없다. **push만 불리했다.**
- sim 작성자(커밋 계정 f56e751)에게 의도였는지 확인 필요.
