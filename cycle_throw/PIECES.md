# 조각 모드 (`GP8_MODE=pieces`)

스킬이 "실행"하지 않고 **조각(`MotionPiece`)을 돌려주면**, 조각 서버가 모든 조각을 **하나의 실제 움직임 계획 + 하나의 명령 보정**으로
이어서 실행한다. 던지기(팀원 플래너)와 push(우리 PushSkill)가 섞여도 정지 넘겨주기, 필터 정착 대기, 컨트롤러 전환,
명령 평활화가 없다. 나중에 강화학습 정책이 들어갈 자리는 그대로 `ActionSelector`(`ctx.skill_for`)다.

## 구조

```
앱 (로봇 PC) PieceRunner                       piece_link.py (robot6, 팀원 플래너 폴더에서 실행)
  벨트 순서로 다음 단계들을 정함                  단계 목록을 하나의 "실제 움직임" 으로 계획
  ctx.skill_for(obj) -> throw | push              throw : rn2 (던지기 한 사이클), 릴리즈 창 끝에서 움직이는 채로 나감
  throw: PlannerThrowSkill (무엇을, 어느 통)       push  : F(U) = 컨트롤러 필터를 통과한 스트로크 명령
  push : PushSkill.plan_piece                     사이  : p2p (움직이는 상태 -> 목표 위 -> 내려감)
         (백스윙부터 스트로크 명령 + 발사 시각)      명령  : rt_inv 한 번 (접촉점에서만 나눔) -> 버퍼
   ──plan {steps: [throw, push.., pick]}──▶
   ◀──cmd / suc / planned────────────────
```

### push 를 F(U) 로 계획하는 이유
실제 팔이 skill 모드에서 하는 push 는 명령 U 가 아니라 **U 가 컨트롤러 필터(지연 40 ms + 200/80 ms 이동평균)를 거친 움직임**이다.
그 움직임(F(U), 플래너가 식별한 필터 모델로 계산)을 목표로 두면:
- 눈으로 맞춘 push 의 모양과 **물리적 접촉 시각이 그대로** 재현된다 (발사 시각 = skill 모드와 같은 식, `PUSH_PERCEPTION_LAG` 그대로).
- F(U) 는 이미 부드러워서 플래너 보정이 명령 제한 안에서 명령을 다시 만든다 → 버퍼 제한 검사를 저절로 통과 (평활화 불필요).

### 단계 사이 연결 (정지 넘겨주기 없음)
- 던지기 다음이 push: 릴리즈 창 끝 상태(움직이는 중) → 백스윙 위 (높이 0.12) → 백스윙 (정지) → 캔이 오면 F(U)
- push 다음: 스트로크 끝 상태 → 그 자리 위로 (0.12, 벨트 위 물체를 피함) → 다음 대상 위 → 내려감
- 던지기 다음이 던질 물체이고 한 사이클로 닿음: rt_cont 의 직접 사이클 그대로
- 남은 게 없으면: push 뒤면 친 자리 위 (0.12) 에서 정지, 아무것도 안 했으면 고정 대기점
- 명령은 요청 전체를 한 번에 맞추고 접촉점에서만 나눈다 (긴 구간은 500 샘플마다 더 나눔). 접촉점 상태는 정확히 맞춘다.

### 끝부분을 열어 두기 (요청 사이에 서지 않기)
요청이 정지로 끝나면 (뒤에 할 일이 아직 안 보일 때) 그 끝부분 명령은 **0.1 s 조각으로 나눠 두었다가 마감 직전에만** 보낸다.
그 사이 다음 요청이 오면, 아직 안 보낸 첫 경계 b 에서 커밋을 멈추고 b + L (필터 길이 0.32 s) 까지는 옛 끝부분을 따른 뒤 그
상태에서 새 단계를 잇는다 (옛 명령이 그만큼 영향을 주므로; push 뒤면 들어올리는 중간). 성공하면 b 뒤의 옛 끝부분은 버린다.
못 하면 (시간 부족 등) 옛 끝부분이 그대로 나가 정지한다 = 이전과 같다. 그래서 한 요청의 push 수에 상한이 필요 없다
(`GP8_PIECE_PUSH_MAX` 는 한 요청에 담는 양일 뿐, 연속 캔은 이어서 친다).

### 안전 경로를 먼저 (계산이 늦어도 팔이 서지 않게)
던지기 계산이 끝나면 팀원 방식의 "던진 뒤 고정 대기점" 경로를 바로 늦게 보내기 조각으로 대기열에 넣는다. push·다음 집기 계획은
그 첫 조각이 아직 안 나갔을 때만 대체하고, 이미 나갔으면 버린다 (그 물체들은 다음 요청에서 다시). 이어 붙이기도 같은 규칙.
앱이 오류로 멈출 때는 석션을 끈다.

### 버퍼 쓰기 여유
상수 대신 **쓰기마다 잰 왕복 시간**(쓰기 → 컨트롤러 확인, 95 백분위 × 1.5) + 컨트롤러 min_lead 3 틱. 잰 값이 5 개 미만이면 40 틱.
조각 앞의 빈 구간은 앱이 채우지 않는다: 컨트롤러가 마지막 명령으로 채운다 (`sample_buffer.cpp`). 그래서 모든 쓰기가
조각 자신의 여유 (0.3 s 이상) 를 갖는다 (쉰 뒤 "지금 + 10 ms" 로 채우던 쓰기가 실기 거부의 원인이었다).

## 실행

```bash
GP8_DEMO_MODE=pieces GP8_DEMO_CHECK_ONLY=1 gp8_cycle   # 로봇 없이 점검 (robot6 계획 + 가짜 버퍼)
GP8_DEMO_MODE=pieces gp8_cycle                         # 실기 (나머지 설정은 cycle 모드와 같다)
```
점검만: `python -m gp8_control.tools.cycle_dry_check --mode pieces --host robot6-planner --push-test 0.5`
(`--push-test`: 첫 물체 전에 대신 push 단계 하나 (J1 ±0.15 rad 명령) 를 push 경로로 계획)

## real-to-sim 기록과 재생

`gp8_cycle` 은 실행마다 `~/gp8_logs/cycle_demo/<시각>/record/` 에 기록한다 (`GP8_RUN_RECORD=0` 이면 끔; 다른 실행은
`GP8_RUN_RECORD_DIR=<dir>`). cycle·조각 모드, 실기·트윈 모두 같은 형식 (`utils/run_record.py`):
`events.jsonl` (링크 송수신, 버퍼 쓰기, 석션, 검출 원본, 추적 10 Hz, 트윈은 스폰·착지), `joints.f64` (실제 관절),
`cmd.f64` (팔에 준 명령, 효력 시각 기준). 읽기는 `tools/real2sim.py` (rclpy·mujoco 없이):

```bash
python -m gp8_control.tools.real2sim summary RUN          # 한 일: 계획, push/던짐, 늦은·거부된 조각, 석션, 관절 Hz
python -m gp8_control.tools.real2sim track RUN --fit      # 실제 관절 vs 명령·필터 모델 (오차, 최적 지연, 최악 순간, 필터 맞춤)
python -m gp8_control.tools.real2sim spawn RUN -o obj.json  # 추적된 물체 흐름 -> 트윈 스폰 스크립트
GP8_SIM_SPAWN_SCRIPT=obj.json GP8_SIM_BELT_SPEED=<출력값> ...   # 트윈이 같은 물체를 같은 플래너 시각에 받음
python -m gp8_control.tools.real2sim compare REAL TWIN    # 물체별 행동 (push/던짐/없음)·계획 접촉 시각 비교
```

로컬 검증 (2026-11-24, 트윈 30 s 섞어서): 기록 켬/끔 처리 결과 같은 수준 (계획 시간 부족 건너뜀 1~2), 재생 트윈이
원본과 **19/19 같은 행동, 접촉 시각 차 0.02 s 이내**. 로봇 없는 버퍼 점검 PASS (명령 10251 샘플 = 틱).
트윈 자신의 추종: `box200_80` 대비 관절 RMS 1.3°, 최적 추가 지연 +20 ms (MuJoCo PD) 에서 0.15° — 실기 값과 비교할 기준.
push 뒤 벨트에 남은 물체가 하류에서 다시 잡힌 추적은 `spawn` 이 버린다 (처음 보인 위치가 0.3 m 이상 하류).

### 실기 기록 결과 (2026-11-24, 가상 물체)
카메라 없이 가상 검출 (`/camera_debug/detections` 에 실제 벨트 엔코더를 따라 움직이는 물체) 로 실기를 돌렸다:
가상 24 개 (페트 + 캔), 계획 28 번 모두 성공, 버퍼 거부·늦은 조각 0, 석션 18 번, push 6 번.
- 드라이버의 `/joint_states` 위치는 `pos_set` (컨트롤러가 받은 명령) 이다: 명령과 0.44° RMS, +6 ms. 실제 움직임은
  `/dynamic_joint_states` 의 `pos_fdb` (엔코더) 이고 기록은 이것을 `joints_fb.f64` 로 남긴다.
- **엔코더는 팀원 필터 모델 `box200_80` 을 그대로 따른다**: 관절 RMS 0.26°, 최대 3.3°, 최적 추가 지연 −4 ms.
  맞춤 최적 (D 0.036, W1 0.18, W2 0.10) 도 0.17° 로 차이가 작다 → 모델은 바꾸지 않는다.
- 트윈 팔은 같은 모델보다 17 ms 늦었다 (위치 서보 지연 ≈ (kv + 관절 감쇠) / kp, 12000/220). `cycle_sim_config` 는 이제
  120000/700 (4 ms): 모델 대비 RMS 1.1° → 0.42°, 처리 결과는 같은 수준, `sim_smoke` 통과.

### 실기 카메라 실행과 앱 부하 (2026-11-24)
- 실제 물체 34 개 (페트 26, 캔 8): 계획 36 번 모두 성공, 석션 27, push 7. 카메라 위치는 엔코더 이동과 1.02 배로 맞고
  흔들림은 벨트 방향 11 mm, 가로 4 mm. 같은 물체 흐름의 트윈 재생 (인식 지연 0) 이 실기와 34 개 중 33 개 같은 행동.
- 트윈 인식 지연: 조각 모드 트윈은 **0** 이 맞다 (0.28 을 모든 물체에 주면 집기가 3.4 cm 뒤를 잡아 페트 19 개 중 6 개만
  통에 들어감; 실기 집기는 정상). push 발사 보정은 실기 값 **0.28 그대로** (필터 켠 트윈에서 0 / 0.10 / 0.18 / 0.28 중
  0.28 이 가장 정면으로 세게 맞힘: 맞은 뒤 캔 속도 중앙값 1.62 / 2.06 / 2.84 / 3.63 m/s). 0.28 의 대부분은 컨트롤러 필터
  지연이고, 필터 없는 RL 트윈 (`sim_experiment/`) 에서는 그만큼 일찍 쳤다.
- 로봇 PC 앱이 대기 중에도 CPU 한 코어의 85~113 % 를 썼다 (py-spy: 활성 시간의 ~75 % 가 rclpy 실행기의 메시지 분배).
  물체가 몰리면 버퍼 쓰기 확인이 200 ms 까지 늦었다. 그래서:
  - 엔코더 기록은 앱 밖 C++ `ros2 bag record` (gp8_cycle 이 띄움) → 끝날 때 `tools/bag_fb.py` 가 `joints_fb.f64` 로 합침.
  - 드라이버 설정 (로봇 PC `motoman_ros2_safety_review/motoman_ROS2`, 커밋 안 함): `joint_state_broadcaster.update_rate: 100`
    (controllers.yaml), SampleBuffer 새 파라미터 `progress_every: 5` (sample_buffer.yaml, 기본 1 = 매 틱;
    `sample_buffer_parameters.yml`, `sample_buffer.cpp/.hpp`). `/joint_states`·진행 메시지 모두 100 Hz.
  - 석션 이벤트는 진행 메시지 도착이 아니라 스탬프로 맞춘 틱 시계로 쏜다 (`BufferClient._ev_loop`).
  - 결과: 앱 CPU 대기 33~47 %, 물체 16 개 몰림 40~50 %, 쓰기 왕복 95 % 12 ms (183 ms 였음), 엔코더 대 필터 모델
    0.42° RMS (이전에 본 최대 29° 는 바쁜 앱이 받은 시각을 찍은 측정 오류).

## RL 학습 환경: 조각 모드 (`rl/piece_env.py`, 2026-11-24)

skill 모드 RL 시뮬레이터 (`rl/gym_env.py`) 에 실기에서 확인한 컨트롤러 필터를 켜면 skill 모드 던지기가 무너진다
(규칙 정책 진단, seed 10 개: throw transparent 0.83 → 0.14~0.24, 현행 규칙 보상 60.8 → 11~15). skill 모드 궤적은
필터 지연을 모르기 때문. 조각 모드는 필터를 계산에 넣어 실기와 맞았으므로, RL 이 고른 행동을 조각 모드로 실행하는
환경을 따로 둔다 (`GP8PieceEnv`, 관찰·행동은 `GP8RecyclingEnv` 와 같음: `[슬롯, 스킬]`, 슬롯 6 = 건너뛰기).

- **결정 시점**: 조각 모드가 다음 단계를 정할 때 (들고 있는 물체 던지기 `RT_AHEAD` 3 s 전, 또는 팔이 비었을 때) 러너
  스레드가 에이전트에게 묻고 `step()` 을 기다린다 (`PieceRunner(decide_fn=...)`). push 를 고르면 같은 요청 안에서
  그 push 가 끝나는 시각 기준으로 한 번 더 묻는다 (규칙처럼 push 최대 2 개 + 집기 1 개를 한 요청에 묶음).
- **가상 시간** (`backends/sim_tick.py`): 플래너 링크가 계산하는 동안은 실제 시간과 같이 흐르고 (계획 지연이 실기와
  같은 비용), 아니면 `GP8_PIECE_WARP_S` (0.05 s) 씩 건너뛴다. 건너뛰기 전에 링크가 그 사이 보낼 명령 조각을 모두
  보내고 응답한다 (`warp` / `warped`, `GP8_PIECE_VIRTUAL=1`). 명령은 트윈의 틱 버퍼 (`SimTickBuffer`, 실기
  SampleBuffer 규칙) 로 들어가 물리 스텝마다 꺼내 쓴다.
- **보상**: 트윈의 물체 결과. 던진 물체는 클래스 통, push 한 물체는 `push_<클래스>` 통이 정답.
- **검증**: 같은 물체 흐름 (19 개) 에서 규칙 정책 + 가상 시간 = 실시간 조각 모드 트윈과 19/19 같은 행동, 석션 85 % /
  91 %, push 명중 57 % / 57 %. 속도는 실시간의 약 2 배 (남은 시간은 대부분 플래너의 실제 계산). 로봇 없는 버퍼 점검과
  `sim_smoke` 통과 (실기 경로는 시계가 `time.monotonic` 그대로).
- 실행: `python -m gp8_control.rl.piece_env --seconds 120 --policy heuristic|random`,
  학습: `python -m gp8_control.tools.train_ppo_smoke --env piece ...` (MaskablePPO, 짧은 학습 확인함).
  링크는 env 마다 로컬 자식 프로세스 (`GP8_CYCLE_PLANNER_HOST` 비움), reset 마다 새로 뜬다 (몇 초).

### 실기에서 정책 통로 확인 (2026-11-24, 브랜치 feat/rl-piece-sim)
`GP8_PIECE_POLICY=heuristic` (규칙을 정책 통로로) 과 정책 없음 (지금 규칙) 을 같은 가상 물체 12 개 (페트·캔 2 s 간격) 로
실기에서: 12/12 같은 행동, 계획 11 번·석션 8 번·push 4 번 모두 같고 거부·늦은 조각·오류 0. 결정 한 번 0.1 ms.
같은 물체 흐름을 `GP8PieceEnv` (가상 시간, 같은 결정 코드) 에 넣으면 12/12 같은 행동, 페트 집기 접촉 시각 0.03 s 이내,
push 는 4 개 중 2 개 0.07 s 이내·2 개 0.3~0.6 s, push 거절 후 던진 캔 2 개는 트윈이 1.3 s 늦게 집음. env 는 실기
push 설정 (도달 0.70, 가속 24) 을 기본으로 쓴다 (이것이 없으면 push 시각이 0.5 s 어긋남). 정책은
`GP8_PIECE_POLICY=<MaskablePPO .zip>` 으로 실기에 넣는다 (`rl/piece_policy.py`; `remaining_time_frac` 는 실행 시작부터
`GP8_PIECE_POLICY_EPISODE_S` 240 s 주기).

## 검증 (2026-11-19)

MuJoCo 트윈 (실시간, 필터 `box200_80`), 페트+캔 1.6 s 간격, 60 s:

| | 페트 통 진입 / 지나감 | 캔 처리 / 지나감 | 처리한 물체 |
|---|---|---|---|
| cycle 모드 (push 시간) | 9 / 5 | 11 / 5 | 20 |
| 조각 모드 v1 (정지 넘겨주기 + 날 명령) | 16 / 0 | 11 / 5 | 27 |
| **조각 모드 (지금)** | **17 / 0** | **16 / 0** (push 20, 던짐 7) | **34** |

- 이동 115 번 실패 0, 명령 조각 77 개 보정 실패 0, 최대 보정 오차 0.18 rad (던지기 조각 수준), 마감에 잘린 계산 0.
- 던지기 + push 한 번 묶음의 접촉 간격 약 2.45 s (실기 v1 은 약 3.9 s). 백스윙에서 캔을 기다리는 시간 중앙값 0.24 s.
- 캔의 통 진입은 트윈에서 모드와 무관하게 낮다 (트윈 push 의 한계). 실기 push 는 F(U) 로 skill 모드와 같은 움직임이어야 하나 접근 경로가 다르다.
- 로봇 없이 점검 (가짜 SampleBuffer, C++ 규칙): PASS, 조각 34 개 수락·거부 0, 틱 계획 일치, push 단계 시험 통과.

## 실기 v1 에서 나온 문제와 처리
- push 명령이 버퍼 가속 검사 (≤ 20 v_max) 를 2~6 배 넘어 거부 → 진행 중이던 집기까지 멈춤: F(U) 계획 + 보정으로 근본 해결 (명령이 보정 제한 안).
- 40 s 쉰 뒤 첫 쓰기가 10 ms 여유로 늦게 도착해 거부: 실측 왕복 시간 기반 여유로 해결.
- 정지 넘겨주기마다 필터 정착 대기 (0.6 s + 1.1 s): 움직이는 상태에서 잇는 계획으로 없앰.
